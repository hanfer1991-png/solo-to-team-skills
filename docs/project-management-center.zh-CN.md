# 项目管理中心（方法与产品蓝图）

> 本文把 [`solo-to-team-skills`](https://github.com/hanfer1991-png/solo-to-team-skills) 的派工、接单、成果回收、证据核验与人工决策逻辑，整理成可落地的项目管理中心蓝图。它是流程与产品规格，不代表本仓库已经提供了管理应用、定时器或自动派工能力。

## 1. 产品定位

**目标：** 让一个负责人能统筹多个 AI 助手或执行人，清楚知道每项工作由谁执行、何时回收、成果在哪里、凭什么通过，以及谁做最终决定。

**核心闭环：**

`目标 → 登记 → 派工 → 接单 → 到期检查 → 收到成果 → 核验证据 → 人工验收 / 退回 / 取消`

管理中心的首要原则是：**每项未结束的工作都有记录、负责人和下一步；“已接单”不等于“已交付”，“已交付”不等于“已验收”。**

## 2. 设计原则

1. **先登记后派工：** 派工前创建任务记录，明确执行人、收件人、检查时间、交付位置和验收标准。
2. **状态由事件推进：** 接单、成果到达、验收是不同事实，分别记录时间与证据，不覆盖历史。
3. **未验收不关闭：** 只有“已验收”或经授权的“已取消”可从未完清单移除。
4. **证据对应当前版本：** 核验记录关联到实际成果及版本；成果变更后，对受影响的验收项重新核验。
5. **人来做最终判断：** 系统可以呈现事实、缺项与证据，不擅自放行、对外发送、付款、删除或登录。
6. **自动化边界明确：** 若宿主没有定时提醒、跨助手通信或执行能力，由负责人手动检查和通知；不能将技能包描述为自带自动派工或叫醒。
7. **最小可用：** 首版可由表格或 Markdown 台账承载，不要求先建设复杂平台。

## 3. 项目管理中心的信息架构

### 3.1 项目总览

每个项目展示：

- 项目目标、负责人、优先级、计划周期、当前阶段。
- 未完任务数：待接单、执行中、待回收、待核验、退回待补、逾期。
- 最近更新与即将到期任务。
- 阻塞项、需负责人决策项和风险提示。
- 最近验收结果及关联证据。

总览数字只从任务台账的当前状态计算；不得把“已接单”或“已收到成果”算作完成。

### 3.2 任务台账

建议按项目、状态、执行人、收件人、到期时间筛选。每条任务至少包含：

| 字段 | 含义 |
|---|---|
| 任务标识 | 项目内唯一 ID |
| 任务名称 / 目标 | 要做什么，以及预期结果 |
| 执行人 | 负责完成工作的人或助手 |
| 收件人 | 负责接收、核验的人 |
| 交付位置 | 文件路径、链接或其他可定位成果的位置 |
| 验收标准 | 可逐项检查的完成条件 |
| 预计交付时间 | 约定的时间和时区 |
| 下次检查时间 | 负责人计划检查任务的时间 |
| 当前状态 | 由状态机管理，见下节 |
| 当前成果版本 | 成果链接、版本号或内容指纹；至少能辨认核的是哪一版 |
| 风险 / 阻塞 | 影响交付的原因及需要谁处理 |
| 最近事件 | 最近一次接单、提交、退回、验收等记录 |

### 3.3 任务详情

任务详情采用时间顺序显示事件与核验记录，支持查看：目标和验收标准、任务变更历史、执行人回执、成果链接、逐项证据、退回原因、续期记录、验收人和最终决定。关键事实应追加记录，不静默覆盖。

### 3.4 决策与风险区

单独列出需负责人处理的项目，例如：逾期需升级、目标冲突、验收有争议、涉及对外发布或财务操作。界面应把“系统建议”和“负责人决定”明确区分，并记录决定人及时间。

## 4. 任务状态与转换

推荐状态：

- **待派工：** 记录已建立，尚未正式交给执行人。
- **待接单：** 已派出，等待执行人明确接单。
- **执行中：** 已接单，尚未提交成果。
- **待回收：** 到达约定检查点，等待成果或状态更新。
- **待核验：** 已定位到成果，尚未完成验收。
- **退回待补：** 核验发现缺项，执行人需补交；任务仍未结束。
- **已验收：** 收件人依据证据确认全部验收项通过。
- **已取消：** 有权限的负责人明确取消，并记录原因。

常见转换：

```text
待派工 → 待接单 → 执行中 → 待回收 → 待核验 → 已验收
                                      └→ 退回待补 → 待核验
待接单 / 执行中 / 待回收 → 续期（保留原状态和历史预计时间，记录新时间）
未结束状态 → 已取消（仅授权负责人；必须写原因）
```

约束：

- “已接单”只能表明对方接住了工作，不表示成果已到。
- 只有确认成果确实位于约定位置，才能进入“待核验”。
- 有任何验收项未通过，应退回并保留在未完任务中。
- 续期不得抹去旧到期时间；保留每次变更及原因。
- 取消不等同于验收，仪表盘应分开统计。

## 5. 标准工作流

### A. 建立任务

负责人写清：做什么、结果放哪里、何时交、由谁执行和接收、什么时候检查、怎样逐项判断完成。验收条件应可观察、可复核，避免“做得好一点”等含糊表述。

### B. 派工与接单

先登记“待接单”，再发送任务说明。执行人明确接单后追加接单事件，状态变为“执行中”。若无人接单，按负责人设定的检查点提醒、改派或升级；提醒可由宿主能力或人工完成。

### C. 到期检查与续期

到检查时间查看任务状态和约定交付位置。没有成果时不登记“已收到”；记录实际情况，选择续期、升级或调整分工，并告知执行人。

### D. 收到成果

确认交付物可访问且位置正确后，记录成果链接、提交时间和版本，进入“待核验”。仅收到口头“做完了”而无可定位成果，不足以转为待核验。

### E. 证据核验

逐项对照预先约定的验收标准。每项记录结果、核验方法、证据位置及所对应的成果版本。可接受的核验示例：打开并检查文件、对照输入来源、重算结果、按原步骤重新操作。转述或未对应当前成果版本的证据不应视为通过。

### F. 人工判断

全部通过后，由授权收件人作出“已验收”决定；缺项则退回并写明改什么、何时补交及需重核的范围。目标变化时先更新目标和验收标准，再继续执行。涉及付款、发布、删除、登录等高影响动作时，交由本人操作和确认。

## 6. 事件记录格式

事件可采用追加式记录：

`时间｜任务标识｜事件类型｜操作者｜事实 / 说明｜成果或证据链接｜下一步｜下次检查时间`

事件类型建议：`待接单`、`已接单`、`检查`、`续期`、`升级`、`已收到成果`、`核验通过`、`退回`、`已验收`、`已取消`、`目标变更`。

一条精简登记示例：

```text
待接单｜任务标识：P-014｜任务：整理访谈纪要｜执行人：助手甲｜收件人：项目负责人｜交付位置：docs/interview-notes.md｜预计交付：2026-11-18 17:00（UTC+8）｜检查时间：2026-11-18 17:10（UTC+8）｜验收：决定与行动项分节；行动项含负责人和日期；不添加来源未提及的信息
```

## 7. 仪表盘与指标

首版建议提供以下可解释的工作视图，而不是未经验证的绩效评分：

- **未完清单：** 除已验收和已取消外的全部任务。
- **今日检查：** 检查时间已到或即将到的任务。
- **待核验：** 已有成果但尚未验收的任务。
- **逾期 / 阻塞：** 超过预计交付时间或明确标记阻塞的任务。
- **待决策：** 需要负责人选择验收、退回、续期、改目标或取消的任务。
- **历史记录：** 按项目查看已验收、退回和取消事件及其证据。

可以统计任务各状态数量、逾期数量、等待核验时长、退回原因分布，但应注明统计口径。没有对照实验前，不宣称系统必然减少错误、催办或工作时长；指标用于发现流程问题，不直接等同于个人绩效。

## 8. 权限与安全边界

- **项目负责人：** 定目标、优先级、分工和最终取舍；授权验收或取消。
- **执行人：** 接单、推进工作、提交成果与说明；不能替收件人自行标记验收。
- **收件人 / 核验人：** 定位成果、按标准核验、记录证据并提出验收或退回建议；授权范围以项目设置为准。
- **观察者：** 查看项目状态和记录，不修改任务与决定。

任何角色权限应显式配置。管理中心不得存储不必要的凭据；对外发布、付款、删除、登录及其他不可逆或高影响动作要求本人确认。系统自动化只在宿主明确支持并经授权时启用，且应保留操作日志；否则提示由人工执行。

## 9. MVP 建设顺序

1. **阶段一：表格 / Markdown 台账。** 先固定字段、状态、事件格式和未完清单；用一件低风险小任务走通派工到验收。
2. **阶段二：轻量看板。** 增加项目总览、过滤视图、到期提示（由明确配置的提醒能力或人工检查实现）和任务时间线。
3. **阶段三：证据与权限。** 为验收项关联成果版本和证据链接，增加角色权限、变更历史与操作审计。
4. **阶段四：有限集成。** 仅对已验证的宿主接入提醒或任务创建；集成能力、失败处理和人工接管路径分别说明，绝不把“装有技能”写成“全自动运行”。

## 10. MVP 验收清单

- [ ] 派工前能创建任务并填写执行人、收件人、检查时间、交付位置和验收标准。
- [ ] 接单、收到成果、验收分别记录，含操作者与时间。
- [ ] 未验收任务始终保留在未完清单中；退回后仍可继续追踪。
- [ ] 每项验收结论可追溯到具体验收标准、成果版本和证据。
- [ ] 续期、退回、改目标和取消保留原因与历史。
- [ ] 高影响动作不会仅凭 AI 输出自动执行，最终决定由授权的人作出。
- [ ] 没有宿主自动化时，界面和文档如实说明人工检查与提醒责任。
