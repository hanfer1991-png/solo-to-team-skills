# 每日运行说明

## 每天开始：检查未完任务

在 `tasks.csv` 中筛选所有状态不是 `已验收`、`已取消` 的行，逐项检查：

1. **待接单：** 是否收到明确接单回执？没有则按约定时间提醒、升级或改派，并追加事件。
2. **执行中 / 待回收：** 检查时间或交付时间是否已到？联系执行人确认进度；未实际看到成果前，不记“已收到成果”。
3. **待核验：** 打开任务行中的交付位置，检查 `acceptance-checklist.csv` 是否每项都有结果、证据位置和对应版本。
4. **退回待补：** 检查补交时间及新版本；补交后更新成果版本，再核验受影响的条目。
5. **逾期 / 阻塞：** 记录事实、影响、责任人和下一步。续期保留原承诺时间，并在事件流水写明原因和新预计。
6. 更新 `next_check_at`，为每个未完任务设定下一次人工检查时间。

## 派工前：写清任务

每条任务必须至少有：唯一任务 ID、项目 ID、明确目标、执行人、收件人、交付位置、可逐项检查的验收标准、原始预计交付时间和下次检查时间。任务先登记后派出。

发给执行人的任务说明建议：

```text
任务：{任务名称}
目标：{任务目标}
交付位置：{交付路径或链接}
验收标准：
1. {可观察的标准一}
2. {可观察的标准二}
预计交付：{日期时间和时区}
请接单时明确回复“接单”；提交时提供交付位置和版本。若无法按时完成，请说明原因和新预计，不要把新预计当成已批准改期。
```

## 事件怎么记

每次发生状态变化或重要检查，在 `task-events.csv` **追加新行**：接单、到点检查、续期、升级、收到成果、核验、退回、验收、取消、目标变更。事件时间、操作者、事实和下一步必须如实填写。不要以新事件覆盖旧记录。

| 事件 | 记录要求 |
|---|---|
| 接单 | 谁接的、何时接单、当前预计时间 |
| 续期 | 原承诺、新预计、原因、是否由有权限的人批准 |
| 收到成果 | 实际确认的交付位置、提交时间、成果版本 |
| 核验 | 具体标准、核验方法、证据位置、成果版本、通过或未通过 |
| 退回 | 缺项或错误、已告知执行人、补交预计、下次检查时间 |
| 已验收 | 全部标准通过的证据、核验人、最终决定时间 |
| 已取消 | 拍板人、授权依据（如需要）、取消原因 |

## 状态变更规则

```text
待接单 → 执行中 → 待回收 → 待核验 → 已验收
                                  └→ 退回待补 → 待核验
任一未关闭状态 → 已取消（仅授权负责人决定并记录原因）
```

- 接单只说明执行人接下任务；此时成果尚未交付。
- 只有确认成果已在约定位置，才能转为 `待核验`。
- 任何验收项未通过，任务进入 `退回待补`，继续留在未完清单。
- 所有验收项通过后，由收件人作最终人工判断并记录 `已验收`。
- 对外发布、付款、删除、登录等高影响动作由本人确认和执行，不由模板或 AI 自动完成。

## 示例闭环（虚构）

1. 负责人在 `tasks.csv` 建任务 `P-001-T-001`，状态 `待接单`，然后派工。
2. 执行人回复接单：追加事件，状态变更为 `执行中`。
3. 到约定检查点仍未交付：追加检查 / 续期事件，保留 `original_due_at`，记录新预计和批准状态，并设置下次检查时间。
4. 负责人实际打开约定位置，确认文件存在：填 `latest_deliverable_version`，追加“收到成果”事件，状态 `待核验`。
5. 在 `acceptance-checklist.csv` 逐条记录证据和结果。若 C-02 未通过，追加退回事件并把状态设为 `退回待补`。
6. 补交后更新成果版本，对受影响的 C-02 重新核验；全部通过后由负责人记录验收事件，状态设为 `已验收` 并填 `closed_at`。

## 字段口径

- 日期时间使用 `YYYY-MM-DD HH:MM`，并在团队约定中统一时区（示例采用 UTC+8）。
- `original_due_at` 是最初承诺，创建后不覆盖；`current_due_at` 是当前批准的预计时间。
- 执行人提出的新时间先记为建议；仅有授权者确认后，才更新 `current_due_at`。
- `latest_deliverable_version` 示例可用 `v1`、`v2`；版本变化时对相关验收条目补核。
- 证据应能由收件人打开、复算或按步骤复现；“执行人说已完成”不是成果证据。
- 示例数据仅用于说明格式，正式使用前请替换或删除示例行。
